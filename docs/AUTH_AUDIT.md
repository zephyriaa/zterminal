# Authentication audit (2026-09-27)

## Observed production failure

The deployed Cloudflare Worker at `https://zterminal-web.zephyria-inc.workers.dev` returns `enabled:false` from `/api/auth/config`, naming missing `GOOGLE_CLIENT_SECRET` and a PostgreSQL `DATABASE_URL`. `wrangler secret list` confirms that `AUTH_SECRET`, `NEXTAUTH_SECRET`, and `GOOGLE_CLIENT_ID` are stored for `zterminal-web`. Its `/api/auth/providers` initially returned HTTP 500 because the auth route threw on incomplete configuration before reaching its disabled-provider response; the deployed fix now returns HTTP 200 with an empty provider list. The Google Cloud project `zterminal` has a `ZTerminal Web` OAuth client whose authorized origin and redirect URI now target the Worker. Its secret cannot be viewed after creation. The app remains in Testing mode with only the owner's Google account listed. The existing Supabase `zterminal-prod` project was restored from a paused state. Its initially empty public schema now has all 24 application tables from `prisma/postgresql-initial.sql`, with row level security enabled on all 24 by `prisma/migrations/supabase_production_rls.sql`. The missing Worker secrets prevent a real Google login.

The build pipeline also generated Prisma from the SQLite schema for the Worker even though the production auth gate requires PostgreSQL. The OpenNext build command invoked `npm run build`, whose `prebuild` hook generated the SQLite client again. The Worker build now generates the PostgreSQL client with the `pg` driver adapter and invokes Next directly. The actual production database and schema still need deployment verification.

## Current architecture

- Browser: the terminal server page resolves the Auth.js session once and seeds one `SessionProvider`. Auth.js v4 handles Google OAuth at `/api/auth/[...nextauth]`, including state and PKCE cookies. Auth.js creates `User` and linked `Account` records through the Prisma adapter. The account panel displays callback errors.
- Session: Auth.js now uses adapter-backed database sessions, so sign-out removes the server session. The browser receives only the HttpOnly session cookie. Tab focus refetches the session and Auth.js broadcasts session changes across tabs.
- Identity and cloud data: the immutable `User.id` from the verified session is the sole owner key. Profile and cloud workspace APIs query by that ID. Cloud workspaces remain in memory and are cleared on sign-out; local workspaces remain in the device store.
- Web routes: `/terminal` remains public for local research. `/api/user/profile` and `/api/cloud/workspaces` require a session. No other app route currently promises account-only access.
- Landing page: public and static. Its workspace link no longer claims that an anonymous visitor is synced.
- Windows app: the Tauri webview has no secure system-browser callback or app-specific session exchange. The launch screen now states that cloud sign-in is unavailable and continues to support local research. A native PKCE/deep-link exchange needs a separate implementation before this can be enabled.
- Email/password: not implemented in the existing repository. There is no credentials provider, password hash, mail service, confirmation, reset-token delivery, or change-password endpoint. The Google-only UI reflects that limitation. Account linking to an existing email/password account is therefore not applicable yet. Auth.js will reject an unlinked provider identity instead of merging by email alone.
- Research jobs: the legacy Python queue accepted any client-selected workspace ID and let callers fetch or cancel a job by ID. The public web proxy now exposes only stateless validation/conversion operations. The legacy queue's job endpoints require a server-only `RESEARCH_SERVICE_SECRET`, and remain unavailable through the web app until the research service stores and verifies a session-derived owner ID. This deliberately leaves cloud research job execution disabled.

## Deployment checklist

The current checked-in Worker origin is `https://zterminal-web.zephyria-inc.workers.dev`. If a custom domain replaces it, use **that one exact public origin consistently** in every setting below. Preview deployments need their own exact origin and callback. Local development uses `http://localhost:3000`.

1. **Google Cloud Console → project `zterminal` → Google Auth Platform → Clients → `ZTerminal Web`**: the authorized JavaScript origin is `https://zterminal-web.zephyria-inc.workers.dev` and the authorized redirect URI is `https://zterminal-web.zephyria-inc.workers.dev/api/auth/callback/google`. For local testing add `http://localhost:3000` and `http://localhost:3000/api/auth/callback/google` to a development client. Complete consent branding and publish the app before general public sign-in; while it remains in Testing mode, only listed test users can log in.
2. **Cloudflare Worker environment/secrets for `zterminal-web`**: `GOOGLE_CLIENT_ID` and `NEXTAUTH_SECRET` are set. Set `GOOGLE_CLIENT_SECRET` and `DATABASE_URL` securely. The database URL must be a PostgreSQL URL, such as the `zterminal-prod` Supabase session-mode pooler on port 5432. Percent-encode special characters in the password. Keep secret values out of repository files and logs. `wrangler.jsonc` already sets `NEXTAUTH_URL` and `NEXTAUTH_URL_INTERNAL` to the public Worker origin. Rotating the session secret invalidates existing sessions.
3. **PostgreSQL**: the existing Supabase project `zterminal-prod` was resumed. Its previously empty public schema received `prisma/postgresql-initial.sql`, generated from `schema.postgresql.prisma`; a query confirmed 24 tables. The SQLite migrations are for local development and are not PostgreSQL migrations. Verify live connection and Auth.js CRUD after the database URL is configured.
4. **Supabase**: the deny-direct-client script in `prisma/migrations/supabase_production_rls.sql` was applied, and a query confirmed row level security on all 24 public tables. The trusted server connection still needs a live test after its secret is configured. Auth.js sessions are not Supabase Auth JWTs, so `auth.uid()` policies cannot identify these users. The browser must not receive a privileged database key.
5. **Cloudflare caching**: leave `/api/auth/*`, `/api/user/*`, `/api/cloud/*`, and `/terminal` uncached. The checked-in Worker proxy caches only immutable static assets, and Next sets private no-store headers for account paths.

The Worker uses Prisma's PostgreSQL driver adapter with Cloudflare's `nodejs_compat` support. This removes the hosted Prisma Accelerate dependency. The current `zterminal-prod` Supabase project has its application schema but still needs its Worker connection secret; the adapter build alone does not enable login.

## Verification and remaining work

Automated tests exercise the production configuration gate, database-session selection, owner-scoped cloud CRUD, and clearing fetched cloud state while retaining local state. The live Worker response establishes why the current login is disabled. A real Google login, callback, new/returning profile, sign-out, refresh, multi-tab propagation, database migration, and Windows callback cannot be confirmed without configured production secrets, a durable database, and a Google test account. Email/password, native authentication, and owner-scoped research jobs require additional product and infrastructure work; do not advertise them as available.
